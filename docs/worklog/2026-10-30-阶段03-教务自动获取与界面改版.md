# 阶段 03:教务自动获取课表(统一身份认证)+ 界面改版

> 本记录由 WorkBuddy 生成(主开发工具)。日期:2026-10-30。

## 一、阶段目标与当时的做法

**目标**:① 界面美化并适配屏幕——周一到周日**同屏展示,不左右滑动**;② 尽量做到**零操作自动获取课表**(用户在「我的」里配置一次学号密码)。

### 1.1 自动获取的可行性实测(全部匿名抓取真实站点,未使用任何猜测)

| 事实 | 实测证据 |
|------|----------|
| 登录走**统一身份认证**(与用户说明一致) | `GET https://jwxt.wmu.edu.cn/sso/jziotlogin` → 302 → `https://authserver.wmu.edu.cn/authserver/login?service=http://jwxt.wmu.edu.cn/sso/jziotlogin` |
| 认证服务器为金智 authserver,表单 `POST /authserver/login?service=…` | 字段 `username`(学号) / `password` / `execution`(服务端下发) / `_eventId=submit` |
| **首次登录不需要验证码** | 验证码容器 `<div id="captchaParent" style="display: none;">` 默认隐藏(仅失败若干次后由服务端要求) |
| 密码**无前端加密**,HTTPS 明文提交 | 页面无任何 AES/RSA/salt 加密 JS;唯一外链 `init.js`(4.5KB)不含加密逻辑 |
| CAS 回跳为 **http** 协议,需定点放行 | `service=http://jwxt.wmu.edu.cn/sso/jziotlogin` → 因此加 `network_security_config` 仅对两个校园域名允许明文 |
| 裸 curl/HEAD 会被 WAF 拦(403) | 需带浏览器 UA;HEAD 直接 403,GET 正常 |

**结论**:零操作自动获取**可行**。

### 1.2 做法

1. `jwxt/JwxtClient`:按主机分别保管 Cookie(不把教务会话发给认证服务器)→ SSO 登录(账号+密码+execution)→ **会话校验**(教务首页可访问且不跳登录页)→ 取个人课表查询页 HTML → **从页面里发现**导出链接 → 逐个请求并按 `%PDF` 魔数校验 → 返回 PDF 字节。
2. `security/SecureStore`:账号密码用 **Android Keystore 生成的 AES-256/GCM 密钥**加密后存应用私有 SharedPreferences;不写日志、不上传、可一键清除。
3. 网络策略:`res/xml/network_security_config.xml` 默认仅 HTTPS,**仅** `jwxt.wmu.edu.cn`、`authserver.wmu.edu.cn` 允许明文(CAS 回跳所需)。
4. 「我的」页新增「教务账号(自动获取课表)」卡片:配置/修改/清除 + 学号打码显示;「课表」页顶部新增「自动获取」。
5. 自动获取流程复用第二阶段同一条链路:PDF → `WmuTimetableParser` → **预览校正** → 事务保存;失败时给明确原因并提供「诊断」按钮(记录每一步 HTTP 结果、发现的候选链接,学号打码)。
6. 界面改版:网格改为**权重布局**(7 天同屏、仅纵向滚动)、今日列高亮、课程卡片圆角与配色统一、周次选择器显示**日期区间**(如 第9周 · 10/27-11/2);主题补齐 `surfaceContainer` 系列颜色角色,修掉导航栏/FAB 退回 Material 默认紫色的问题。

## 五、内置浏览器白屏问题与修复(2026-10-30 晚,用户反馈)

**现象**:内置浏览器点「统一身份认证」后白屏。

**参考项目佐证**(用户提问:参考的 GitHub 里有没有提到?)—— 有直接实现证据,`wakeup-course-schedule` 的
`schedule_import/WebViewLoginFragment.kt` 中登录 WebView 的配置:

| 参考项目设置 | 我原来的设置 | 结论 |
|--------------|--------------|------|
| `mixedContentMode = MIXED_CONTENT_ALWAYS_ALLOW` | `MIXED_CONTENT_NEVER_ALLOW` | **白屏主因**:教务在 https 页面里混用 http(CAS 回跳/内嵌),被我拦截 |
| `javaScriptCanOpenWindowsAutomatically = true` | 未设置 | SSO 常以新窗口打开,需允许 |
| `useWideViewPort = true` + `loadWithOverviewMode = true` | 未设置 | 固定宽度登录页可能渲染成空白 |
| `domStorageEnabled = true` | 已设置 | 一致 |

**修复**:
1. 按参考项目改为 `MIXED_CONTENT_ALWAYS_ALLOW`;补 `setSupportMultipleWindows(true)` +
   `WebChromeClient.onCreateWindow`(新窗口链接并入同一 WebView)、`useWideViewPort`、`loadWithOverviewMode`;
   本页仍保持:禁 `file://`/`content://`、拦截非 http(s) 跳转。
2. **把白屏变成可诊断信息**:`onReceivedError`/`onReceivedHttpError` 主框架失败时显示错误码与 URL;
   地址栏下方显示当前 URL,并新增「后退 / 刷新」按钮。
3. 自动获取的 HTTP 客户端改用 **WebView 的 UA**、表单 POST 补 `Origin` 头,尽量与内置浏览器请求一致,
   降低被风控判定为可疑(进而要求验证码)的概率。

## 六、v0.2.0 修正:获取顺序改为"会话优先" + 浏览器可用性补强

**用户真机反馈(诊断截图)**:自动获取失败,诊断显示
`① 访问 SSO 入口 → authserver 登录页 HTTP 200 → 本次登录被要求图形验证码 → 使用内置浏览器会话(Cookie 1 项) → 教务首页 HTTP 302`

**据实分析(两条独立结论)**:
1. **Cookie 仅 1 项 + 教务首页 302** ⇒ 内置浏览器里**登录并未真正建立教务会话**(1 项多为网关/路由 Cookie)。
   即真正卡点是「浏览器登录」,而不是解析或导出发现。
2. **"被要求验证码"是客户端会话被风控判决的结果**:再次核对保存下来的 authserver 登录页,
   `$("#captchaParent").show(); config.captcha = {type:'image', id:'…'}` 该 `<script>` 无条件出现,
   且带服务端生成的 captchaId ⇒ 服务端**按会话/风控**决定是否要验证码;裸 HTTP 客户端新建的会话被判定可疑。
   ⇒ 结论:**账号密码裸 HTTP 登录不可靠且有用锁风险(阈值 5),应降为备用路径**。

**本次改动**:
- 「自动获取」**改为会话优先**:① 复用内置浏览器会话 → ② 无会话才尝试一次账号密码登录(不重试)。
- `JwxtClient` 登录前**先预热教务登录页**(镜像真实浏览器:先落 jwxt 再跳 SSO),并记录各主机 Cookie **名称**(不含值)。
- 内置浏览器新增:
  · 「**获取课表**」按钮 —— 用 WebView 会话直接取课表页 → 发现导出链接 → 拉 PDF → 交给课表页导入(不依赖页面下载按钮);
  · 「**自检**」按钮 —— 显示当前 URL 与两域 Cookie **名称**,直接判定"登录是否真的成功";
  · 「**桌面版/手机版**」UA 切换 —— 手机 UA 下渲染异常时的备用开关。
- 版本管理:versionCode 2 / versionName **0.2.0**;开启 buildConfig,「我的 → 关于课伴」显示实际版本号;
  交付的 APK 另存为 `docs/课伴-v0.2.0-debug.apk`。

**仍未验证(如实标注)**:内置浏览器白屏的真实原因(需用户提供白屏当刻截图/错误码)、
登录成功后导出链接能否被发现。两处都要真实账号实测。

## 八、v0.2.4 白屏真正根因(Codex 真机定位,用户确认已解决)

**根因**:authserver 顶层 HTML 为 iframe 容器(`<iframe id="loginIframe">`),站点脚本按 UA 把 iframe
指向 login-mobile.html / login-normal.html。真机 WebView 中该 iframe **高度坍缩为 0**(Visited 宽约 394 CSS 像素、
`readyState=complete`、`forms=1`、`inputs=2` 但布局高度 0) → 表单其实已加载,只是**看不见**,表现为"白屏"。

**Codex 的修复**:仅对 `https://authserver.wmu.edu.cn/authserver/login` 这一个页面,
在加载完成与布局变化时按原生视口与 CSS 宽度比例显式设置 loginIframe 及 html/body 高度;
同时修正 `onCreateWindow` 复用父 WebView 的实现问题(改单窗口导航)、默认改回原生手机 UA。
真机复测:iframe 高度 0 → 495.58 CSS 像素,登录页正常显示。**用户确认"终于好了"。**
详见 `docs/教务登录白屏-Codex复核.md`。

**我此前判断的更正**:① 把 mixedContent 当主因、② 把 UA 伪装当最可能根因、
③ 把"缺 JSESSIONID"当"非正常登录页"的证据 —— 三项均**降级为待验证假设**;
真正原因是 **iframe 高度坍缩**。教训:不要只看顶层 `body.innerText`(它不含 iframe 内文字)就下结论。

**会话已打通(用户 v0.2.5 前截图)**:教务首页 `HTTP 200, 长度 71985, cookie=JSESSIONID,route` ⇒ 登录成功。
