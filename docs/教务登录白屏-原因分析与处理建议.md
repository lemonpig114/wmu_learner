## 一、现象

在内置浏览器里打开教务入口、点击"统一身份认证"后**页面白屏**；随后在课表页点"自动获取"失败。

## 二、已确认的事实（硬证据）

### 证据 1：失败点确定在"浏览器登录"环节，不在解析或导出

用户在课表页点"自动获取"得到的诊断原文：

```
① 访问教务 SSO 入口,获取统一身份认证登录页
最终地址主机:authserver.wmu.edu.cn (HTTP 200)
本次登录被要求输入图形验证码(服务端风控判定)
使用内置浏览器会话(Cookie 1 项)
教务首页返回 HTTP 302, 长度 0
```

推断依据：
- `教务首页返回 HTTP 302` = 带着这份 Cookie 访问教务首页仍被弹回登录页 → **会话无效**
- `Cookie 1 项` = 正常登录成功后 jwxt 会有 `JSESSIONID` 之类的会话 Cookie；只有 1 项说明**登录从未真正完成**

### 证据 2：浏览器确实到达了认证服务器，但服务端没给会话

用户在内置浏览器点"自检"得到的原文：

```
当前地址:https://authserver.wmu.edu.cn/authserver/login?service=http%3A%2F%2Fjwxt.wmu.edu.cn%2Fsso%2Fjziotlogin
jwxt.wmu.edu.cn Cookie:route
authserver Cookie:_7da9a, service
判断:仍在登录相关页面(登录可能未完成)
```

两点关键：
- 请求**确实发出去了**（地址已是 authserver 的登录页 URL，服务端也回了 `Set-Cookie`）→ 不是网络不通、不是被我拦截
- **authserver 侧没有 `JSESSIONID`**（金智 CAS 登录页的正常会话 Cookie）→ 到达的很可能**不是真正的登录页**，而是中间页/风控响应；或页面没能正常渲染

### 证据 3：客户端被"要求验证码"是风控判决，不是恒定行为

我抓取并保存了 authserver 的登录页（`.analysis-local/jwxt/authserver_login.html`），页面内联脚本为：

```js
$("#captchaParent").show();
$("#captchaLabel").show();
config.captcha = { type: 'image', id: '3708747673' };
```

- 该脚本**无条件执行**，且 `id` 是服务端**动态生成**的 captchaId
- 而**用户用自己浏览器登录不需要验证码**（用户实测）
- 同一批匿名请求还曾被 WAF 返回 403

**结论：验证码由服务端按会话/风控现判。** 我方裸 HTTP 客户端新建的会话被判为可疑 → 被要求验证码。
⇒ **"账号密码纯自动登录"不可靠，且失败 5 次会锁账号（页面 `dlsbsdsj=5`），已降为备用路径。**

## 三、根因判断（按可能性排序）

### ① UA 特征导致教务站返回异常页面 —— **最可能，且参考项目已给出解法（有代码证据）**

参考开源项目（下节详述）在初始化 WebView 时**默认**做了 UA 伪装：

```kotlin
// WebViewLoginFragment.kt 第 159 行（initWebView 内，默认执行）
wv_course.settings.userAgentString = wv_course.settings.userAgentString
    .replace("Mobile", "eliboM")
    .replace("Android", "diordnA")
```

它把 UA 里的 `Mobile`、`Android` 两个词**改写成看不出含义的字符串**，页面就识别不出这是 Android 手机浏览器。
该项目还专门做了一个开关（第 168–170 行）来切换这项伪装 —— 说明**这是为了绕开教务站点对手机 UA 的适配问题而刻意加的**。

这也解释了证据 2 里"请求通了、但没拿到正常登录页"的矛盾：**请求头里的 UA 让服务端返回了另一套（手机版/中间）响应**。

> 我方请求与真实手机的差异还有一处：Android WebView 的 UA 含 `wv` 标记和 `Version/4.0`，部分校园 WAF/反爬会据此拦截或降级响应。

### ② 手机所在网络出口被 WAF 拦 —— 有可能，需实测区分

- 我这边（电脑、经代理）用普通浏览器 UA `curl` 同一 URL，**能拿到完整真实登录页（11330 字节，含表单与 execution 隐藏项）**
- 用户手机当时走的是**移动数据（5G）**，出口 IP 与校园网完全不同
- 若手机自带浏览器打开同一 URL 也白屏 ⇒ 属站点/网络侧，与 App 实现无关

### ③ 页面渲染问题（缩放/内核） —— 可能性较低

已按参考项目配置 `useWideViewPort` + `loadWithOverviewMode`，本次又补 `textZoom=100`、缩放控件。
若仍白屏，用"页面内容探针"（见第五节）即可分辨是"页面真空白"还是"内容在但没显示"。

### ④ 证书问题 —— 可能性低，且我**不打算放行**

参考项目对**所有站点**直接 `handler.proceed()`（接受任何证书）。我方**明确不做**：那会让校园网内的中间人可窃取登录口令。
本次只加了"证书失败时报告错误并拒绝加载"，便于定位而不是掩盖。

### 从它这里得到的三条有用信息

1. **WMU 的教务入口**：`jwxt.wmu.edu.cn`，属"新正方教务（TYPE_ZF_NEW）"，走 **WebView 登录 + HTML 解析**。
   它没有 PDF 解析——**我们的 PDF 导入路线是自研的**，与此项目无关。
2. **登录用 WebView 的关键配置**（本次已按此对齐）：
   - `mixedContentMode = MIXED_CONTENT_ALWAYS_ALLOW`（教务在 https 页混用 http）← 对应上一轮白屏修复
   - `javaScriptCanOpenWindowsAutomatically = true`（SSO 常以新窗口打开）
   - `useWideViewPort = true` + `loadWithOverviewMode = true`（固定宽度登录页可能渲染成空白）
   - **`userAgentString` 的 `Mobile/Android` 伪装** ← 本轮新增，最可能直接解决白屏
3. **它没做的事**：没有处理 CAS 统一身份认证的跳转链、没有 PDF 导出、没有"下载拦截"。
   所以**会话复用 + PDF 导出发现这条链路仍由我们自研**，需要真机实测才能确认。

## 五、本次已做的改动（v0.2.2，供你测试）

1. **内置浏览器默认启用 UA 伪装**（`Mobile`→`eliboM`、`Android`→`diordnA`），与参考项目一致
2. **UA 三态按钮**：点一下在 `UA:伪装`（默认）→ `UA:桌面` → `UA:原生` 之间切换并自动刷新 —— 用来一键区分 ①/② 两种原因
3. **「自检」升级为"页面内容探针"**：除 URL 与 Cookie 名称外，还会显示
   - 页面标题、`readyState`、`body` 子元素个数、HTML 长度、可见文本长度、正文前 300 字
   - 这样"白屏"是**真空白**还是**内容在但没显示**，一眼可判
4. **自动获取改为"会话优先"**：先复用浏览器会话；无会话才尝试一次账号密码（不重试，避免锁号）
5. 自动获取的 HTTP 客户端**改用与浏览器完全相同的伪装 UA**，避免两处请求特征不一致又被风控
6. 证书校验失败时**报告并拒绝**（不擅自放行）
7. 版本号机制：`versionCode 4 / versionName 0.2.2`，「我的 → 关于课伴」可自查
